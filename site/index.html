A second Linux screen, over one cable.

FoxLoop turns a Samsung Galaxy Tab into an extended desktop display — and into a drawing tablet, with the S Pen's pressure, tilt, hover and side button all reaching Linux as a real digitiser would.

55ms

Glass to glass, measured with a camera rather than a log line.

  • 4096pressure levels from the S Pen, plus tilt and about a centimetre of hover
  • 0kernel modules, out-of-tree drivers or firmware blobs to install
  • 1USB cable, and one udev rule that needs root exactly once

Pressure and tilt, in the apps you already draw in

The pen arrives as a graphics tablet, not as a mouse. It is created through uinput, the same facility a Wacom driver reports through, so an application that already understands a Linux digitiser understands this one — with no plugin, no driver and nothing to configure.

How it works

Two programs and a cable. A daemon on your computer creates a virtual monitor, captures it, and encodes it to H.264 on the GPU. An app on the tablet decodes the stream and draws it. Pen and finger input travel back along the same cable and become real Linux input devices.

None of that needs new kernel code. Screen capture goes through PipeWire and the desktop's own screen-cast machinery — the same plumbing OBS and Sunshine use. Input goes through uinput, the standard Linux virtual-input facility.

FoxLoop needs root exactly once, to install a single udev rule granting your user access to /dev/uinput. That rule is byte-for-byte the one Steam ships, so on a machine with Steam installed it changes nothing. Nothing else runs as root, nothing is added to your groups, and nothing starts at boot.

What you need

An Android device, ideally with an S Pen

Any Android device that can act as a USB accessory works as a display — a phone will do. For pressure and tilt it needs a Wacom EMR S Pen: Samsung Galaxy Tab S9 FE or newer, S10 FE or newer, which is what FoxLoop is built and measured against.

KDE Plasma or GNOME

On Wayland. The virtual monitor is made through compositor-specific machinery and there is no portable way to do it, so nothing else is supported yet.

A GPU that encodes H.264

Through VAAPI, which means Intel or AMD graphics. NVIDIA does not work. The encoder is hardware-only, with no software fallback. To check:

vainfo | grep -E 'VAProfileH264.*EncSlice'

Nothing printed means FoxLoop will not run.

What it does

  • A real second display, not a mirror: windows move onto the tablet and keep running there.
  • Plug the tablet in and it starts on its own — the daemon connects straight to the tablet, with no adb relay in the way.
  • Full S Pen input: pressure, tilt, hover, and a side button you can remap to right click, middle click or eraser.
  • Multi-touch gestures — two-finger scroll, pinch to zoom, tap to click — recognised the way a laptop touchpad's are, and configurable in the same settings panel.
  • Rotate the desktop by any quarter turn. A portrait desktop then fills the landscape panel exactly.
  • Run the desktop smaller than the panel, so everything on it is bigger.
  • A settings screen on the tablet for rotation, desktop size, picture quality, frame rate, pointer mode, gestures and the pen's side button.
  • Keeps the tablet awake while a desktop is on it, and lets it sleep when there is not.
  • Recovers on its own from a pulled cable, an app restart or a daemon restart.

Where it stands

The core path works end to end on KDE Plasma — display, pen, multi-touch, auto-launch and auto-reconnect are all in place, and the latency target was met. Three things are worth knowing before you try it.

GNOME support is written but untested

GNOME's compositor has its own virtual-monitor interface, which fits better than KDE's — it creates the display and streams it in one step, with no picker dialog. That path is implemented, compiles and is unit-tested, and the daemon selects it automatically on a GNOME session. Nobody has yet run it against a real GNOME desktop, because the only machine this is developed on runs Plasma. The daemon logs every stage of setup; a bug report with that output is exactly what it needs.

Every measurement comes from one device

A Galaxy Tab S9 FE+, on one laptop, on KDE Plasma. The 55 ms figure is honest and repeatable there. It is not a survey.

The tablet often starts out mirroring

A known gap on KDE: the new display frequently comes up duplicating your main screen instead of extending it, and has to be switched over by hand in display settings. Whether GNOME behaves the same way is one of the things a first real run there would answer.
